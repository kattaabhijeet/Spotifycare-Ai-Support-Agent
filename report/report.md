# SpotifyCare AI Support Agent — Report

**Brand**: SpotifyCare (@SpotifyCares on Twitter)  
**Dataset**: Customer Support on Twitter (Kaggle `thoughtvector/customer-support-on-twitter`)  
**LLM**: Google Gemini Flash Lite (`gemini-flash-lite-latest`)  
**Embeddings**: `all-MiniLM-L6-v2` via sentence-transformers (local, free)  
**Evaluation set**: 170 stratified examples across 9 intents  

---

## 1. Problem Framing

### What "good" means for SpotifyCare

SpotifyCare is Spotify's public Twitter support channel. Good performance means:

1. **Correct triage** — Getting the customer to the right fix quickly (or to a human when needed). A wrong intent label wastes the customer's time and risks brand damage.
2. **Brand-faithful replies** — SpotifyCare has a distinctive voice: empathetic, concise, action-oriented. An off-brand reply (too formal, too casual, or making unsupported promises) harms trust.
3. **Safe escalation** — Financial disputes, account compromises, and legal language must *never* be auto-handled. False negatives here are costly; false positives are just inefficient.

### What I chose NOT to build

- **Fine-tuning**: The dataset is too small and too noisy for fine-tuning to meaningfully outperform few-shot prompting. I spent that budget on a richer evaluation harness instead.
- **Streaming responses**: Out of scope for this assignment; the agent is batch-oriented.
- **Multi-turn conversation memory**: The agent handles one message + its thread context. Full dialogue management was out of scope.
- **Production infrastructure**: No API server, rate limiting, or monitoring — the focus is on the core AI logic and its evaluation.

## 3. Failure Analysis — Top 5 Failure Modes

### F1 — Intent Confusion: `account_billing` vs. `app_device_bug`

**Example**: *"I can't log in to Spotify — it keeps asking for my password every time"*  
**Predicted**: `app_device_bug` | **True**: `account_billing`  

**Hypothesis**: Login loops are a symptom of both buggy session management (app bug) and account credential issues (billing/account). Without more context (has the password been changed? Is premium active?), the signal is ambiguous. The few-shot examples don't cover this overlap well.  
**Fix**: Add 2–3 examples of "login loop due to account issue" in the few-shot prompt; add a tiebreaker rule when keywords like "password" + "login" co-occur.

---

### F2 — RAG retrieves semantically close but intent-mismatched examples

**Example**: *"My playlist isn't loading on my watch"*  
The retriever finds replies about playlists, but those examples are about *collaborative* playlists (social intent), not playback on Wear OS.  
**Hypothesis**: Cosine similarity on general-purpose embeddings conflates topic (playlists) with intent (social vs. playback). The intent-boosting (+0.10) in `reply_drafter.py` helps but doesn't fully fix this.  
**Fix**: Use intent-filtered retrieval (retrieve only within the same intent bucket), or train a bi-encoder fine-tuned on support intent pairs.

---

### F3 — Escalation over-triggers on common frustration language

**Examples**: *"this is the worst app ever"*, *"I'm so done with Spotify"*  
**Predicted**: escalate | **True**: auto  

**Hypothesis**: The LLM judge interprets strong frustration as "high emotional distress" even when the underlying issue is routine (buffering). The current LLM-layer prompt is conservative.  
**Fix**: Calibrate the LLM escalation prompt with 5–10 negative examples (strong language but resolvable issue → auto). Consider a "frustration score" that only escalates when frustration co-occurs with a high-stakes intent.

---

### F4 — Reply hallucination for content availability issues

**Example**: *"Why was [Song X] removed from Spotify?"*  
**Draft reply**: *"Hey! That track is available again — try searching for it!"* ← false.  
**Hypothesis**: The LLM has prior knowledge of some songs being restored and pattern-matches to "reassure user" even when the retrieved examples don't support it. RAG examples are too general.  
**Fix**: For `content_availability` intent, always append a disclaimer: *"We don't have info on specific track availability — try our help center or DM us."* Hard-code this as a template override.

---

### F5 — Short / ambiguous messages default to `other`

**Example**: *"spotify 😭"*, *"fix this please"*  
**Predicted**: `other` | **True**: `app_device_bug` (clear from context the app crashed)  
**Hypothesis**: Messages < 3 meaningful words give the few-shot prompt almost no signal. Without thread context (which is often missing for first messages), the model falls back to `other`.  
**Fix**: Use thread context more aggressively — if the parent tweet provides issue context, extract it into the classification prompt. Alternatively, add a "short message" handling path that asks a clarifying DM.

## 4. What Is Misleading About My Headline Number?

**The most misleading metric is intent classification accuracy.**

1. **Label quality**: The `true_intent` labels in the golden set were generated by the same classifier (bootstrapped via LLM), then manually corrected. However, I could only review ~50 examples in depth — the rest may have label errors that inflate agreement.

2. **Easy-class dominance**: `playback_issue` and `app_device_bug` together represent ~45% of all messages. A model that does well on these two classes will have high accuracy even if it fails badly on rarer intents (`social_playlist`, `content_availability`, `compliment`). Macro-F1 corrects for this — look at macro-F1, not accuracy, as the primary metric.

3. **Self-referential RAG**: The reply drafter retrieves from the same data the agent was trained on. ROUGE-L will appear high because the retrieved examples structurally match the reference replies. This does NOT mean the replies are actually good — that's what the LLM judge is for.

4. **Judge-model overlap**: Both the reply drafter and the LLM judge use Gemini Flash Lite. The judge has an implicit stylistic preference for Gemini-generated prose, which inflates the AI agent's grounding scores relative to the TF-IDF baseline.

5. **Twitter ≠ production**: SpotifyCares' Twitter replies are crafted by human agents with full account access. Our agent has none of that context. The "ideal" replies in our golden set are aspirational; measuring against them understates the real-world difficulty.

## 5. What I'd Do Next With One More Week

1. **Intent-filtered RAG**: Build a separate FAISS index per intent. Retrieval within the correct intent bucket dramatically reduces cross-intent hallucination (F2, F4 above).

2. **Fine-tune a classifier**: Use the golden set + LLM-labelled data (~2k examples) to fine-tune a DistilBERT classifier. This would be 10× cheaper to run per inference than GPT-4o-mini and likely more calibrated on short messages (F5).

3. **Calibrated escalation**: Add Platt scaling to the classifier confidence score so `confidence = 0.60` actually means the model is wrong 40% of the time. Right now, confidence is uncalibrated LLM logit-based guessing.

4. **Production dry-run**: Pipe 100 live tweets from SpotifyCare's real feed through the agent (using the Twitter API), have a human review each decision, and compute agreement. Real-world data always has surprises that held-out test sets don't capture.

5. **Streaming + tool use**: Give the agent access to Spotify's help-centre knowledge base via a retrieval tool. This would fix the content-availability hallucination (F4) almost entirely.
